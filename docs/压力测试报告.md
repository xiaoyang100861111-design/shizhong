# 适中后端压力测试报告

测试日期：2026-09-29。测试对象：`server/Shizhong.Api`（ASP.NET Core 8 + Dapper + SQL Server 2022），Release 编译，`ASPNETCORE_ENVIRONMENT=Production`。
测试脚本在 `tools/load/`（用法见那里的 README），以后可以在自己的服务器上重跑。

## 结论

1. **资金类接口在高并发下是正确的**：同一个人同时下 30 单、同一张券同时用 10 次、100 人抢一个红包、转账同时点"收款"和"退回"、并发提现、并发签到、并发领任务等 14 个场景全部通过。修复前后都没有出现多扣、负余额、重复领取，每次压测后"余额 = 流水"的核对也都是 0 个问题。
2. **修复前系统会在并发 100 左右"卡死"**。原因是**数据库连接池被耗尽**：很多接口先拿着一个数据库连接不放，又去申请第二个。并发一高，100 个连接全被"拿着一个、等第二个"的请求占满，所有请求等 15 秒后报 500。受影响的有：同一直播间集中送礼（600 次里 568 次失败）、聊天发消息（并发 100 时全部卡住 15 秒）、直播间列表（并发 100 时 91% 失败），以及混合流量（并发 200 时 p99 35 秒，2.6% 报错）。**已修复**，修复后同样的测试 0 错误。
3. **还发现 4 处死锁 / 竞争问题，都已修复**：热门动态被同时点赞、评论（205 个请求里 162 个失败）；大量观众同时进入同一个新直播间（400 人里 158 人进不去）；两个人第一次互发消息或互送礼物的同一瞬间报 500；群聊加入与读消息之间的死锁（这一处是本次优化中引入的，在测试中发现并已改正）。
4. **性能优化**：App 启动数据、钱包流水、动态、直播间列表等接口的吞吐提高到原来的 1.3～5 倍。混合 App 流量在并发 200 时从 33 次/秒（有报错）提高到约 410 次/秒（0 错误）。
5. **容量结论（仅供参考）**：在这台 4 核的测试机上（API、SQL Server 和压测程序三者共用），混合流量可以稳定处理约 **400 次请求/秒**。几千名会员的规模，高峰在线按 10–15% 估算约 300–450 人，大约只会产生 50–100 次请求/秒，**有 4–8 倍余量**。瓶颈先出现在 SQL Server 的 CPU。

## 1. 测试环境与方法

| 项目 | 说明 |
| --- | --- |
| 机器 | 4 vCPU（Xeon 2.1 GHz）、15 GB 内存，Linux。API、SQL Server 2022（Docker）和压测脚本（Python，单进程）**都在同一台机器上** |
| 数据 | 测试数据生成器（`--seed`）生成的库，压测结束时约有 2,100 名会员、2.1 万笔订单、8.7 万条消息、23.7 万条资金流水、7 万笔礼物 |
| API | Release 版，Production 模式，Kestrel 监听 5089 端口，连接池使用默认值（Max Pool Size 100） |
| 方法 | 闭环加压：固定 N 个并发"用户"不停地请求（N = 10 → 50 → 100 → 200），每档 8 秒。资金正确性测试是在同一瞬间发出全部请求，然后核对结果 |
| 登录 | 登录限流是每个 IP 5 分钟 30 次，所以吞吐测试先登录好几百个测试会员，令牌缓存起来复用；登录和限流另外单独测（第 6 节） |

> **数字只能当作参考**：三个程序在 4 个核上互相抢 CPU，压测脚本自己就要占大约 1 个核。像 `/api/health` 这种极轻的接口，测到的 4,000–5,000 次/秒其实是压测客户端的上限。正式服务器（IIS + SQL Server 单独占用 CPU）的数字应该更好。

RPS = 每秒完成的请求数；p50 / p95 / p99 = 50% / 95% / 99% 的请求在这个时间（毫秒）内完成。

| 7 | 缺少索引：流水按 Id 倒序、通知按时间+Id、订单事件、送出的礼物、1:1 会话的 UserB | 钱包流水 360 次/秒，SQL 占 2.3 个核 | 新迁移 `server/db/migrations/0902_perf.sql`，启动时自动执行 | 钱包流水 1,080–1,550 次/秒 |
| 8 | 动态（动态页、`/data/posts.js`）每次请求都要跑一个约 20–30 ms SQL CPU 的查询；`/data/people.js` 每次都读最多 5,000 个会员 | 动态 75 次/秒（SQL 占 2.5 个核）；posts.js 50 次/秒；people.js 60 次/秒 | 公共动态列表全站共用、每 5 秒刷新一次，再单独查询"我点过赞的"；会员列表共用 20 秒。拉黑、距离、在线状态仍按每个人单独计算 | 动态 370–420 次/秒；posts.js 120 次/秒；people.js 83–94 次/秒 |

## 9. 仍然存在的风险

1. **单进程架构**：在线状态、直播间观众、限流计数都保存在进程内存里，所以只能跑**一个** IIS 工作进程（不能开 Web Garden，也不能多台服务器做负载均衡）。应用程序池回收时，所有实时连接都会断开，App 会自动重连。
2. **SQL Server CPU 是第一个瓶颈**：启动数据（`/core/server.js`）每次要跑约 35 个查询，重度用户（150 个会话、每个 50 条消息）一次要花 10–25 ms 的 SQL CPU。本机最多约 45 次/秒，也就是每分钟约 2,700 次 App 启动。几千名会员足够用，但如果推送之后所有人同时打开 App，高峰会排队。
3. **下单返回的数据很大**（订单、流水、通知等 7 项），每秒约 100 单就到上限了。目前足够，业务量大了以后可以只返回变化的部分。
4. **同一个直播间**每秒大约只能处理 80–110 次送礼（所有人都要更新主播的同一行）。"刷礼物"活动要注意；有需要的话可以改成先把送礼记下来、再异步汇总到主播收益。
5. **`people.js` 和 `posts.js` 会下发全部会员（最多 5,000 个）/ 全部动态（2,000 条）**，由 API 的 CPU 生成，每次约 30 ms。会员超过 5,000 人时，列表会被截断，需要改成分页。动态最多延迟 5 秒显示，people 列表最多延迟 20 秒显示。
6. **后台导出**把最多 10 万行放在内存里生成；仪表盘一次约 0.6 秒的 SQL CPU（只读聚合）。建议不要在高峰期多人同时导出。以后可以改成流式导出，或者给仪表盘加上短时间缓存。
7. **大群**：加入时需要按群锁住，并插入一条系统消息；150 人同时加群时 p95 约 3.5 秒。群成员预览的查询和群人数成正比，群人数上限是 500（`social.groupMax`），在这个范围内没有问题。
8. **登录很耗 CPU**：每次 BCrypt 约 180 ms。有人从大量 IP 撞库（撞库攻击）时，会把 CPU 占满。请在 Cloudflare 上对 `/api/auth/*` 设置速率限制 / WAF 规则。另外，很多手机用户可能共用同一个运营商公网 IP（运营商级 NAT），"每个 IP 5 分钟 30 次"在高峰期可能误伤正常用户，需要观察后再调整。
9. **其他"持有一个连接再开第二个"的写法**：本次用脚本找出并修复了所有明显的地方（40 处）。今后写新接口时请保持这个规则：拿着连接时，调用 `ProjectKeysAsync(user, c, …)`、`DeliverAsync(…, conn: c)`、`PushAsync(…, c)`；不要在拿着连接时再调用 `db.TxAsync`。
10. **测试环境的局限**：API、数据库、压测脚本共用 4 个核，数据库在 Docker（Linux）里，没有经过 Cloudflare 和 IIS。正式上线前建议在正式服务器上，用备份还原出来的库再跑一次 `tools/load`（不要对正式库跑）。

## 10. 正式环境建议设置

**连接字符串**（`appsettings.Production.json`）：

```
Server=127.0.0.1;Database=shizhong;User Id=shizhong_app;Password=…;TrustServerCertificate=True;Encrypt=True;Max Pool Size=200;Application Name=Shizhong
```
- `Max Pool Size=200`：默认是 100。上面的修复已经消除了"卡死"，但热门直播间集中送礼、热门动态这类情况下，大量请求会排队等同一行数据，每个都占着一个连接。多留一些余量更稳妥，SQL Server 应付 200 个连接没有问题。
- `Application Name`：方便在 SQL Server 里区分哪些连接来自这个程序。

**IIS 应用程序池**（在 `部署说明.md` 已有设置的基础上）：
- .NET CLR 版本"无托管代码"，启动模式 `AlwaysRunning`，闲置超时 `0`（部署说明里已有）；
- **最大工作进程数 = 1**（不要开 Web Garden，原因见第 9 节第 1 条）；
- "固定时间间隔回收"默认是 1740 分钟（29 小时），会在白天随机时间把所有实时连接断开。建议改成 0，并加一个"特定时间"回收（例如凌晨 4:00），或者干脆不定时回收；
- 在网站的"高级设置"里打开"预加载已启用"（需要安装"应用程序初始化"功能），这样回收之后程序会马上启动，后台任务（订单自动确认、红包过期、直播心跳、提现等）不会停下；
- 队列长度保持默认的 1000 即可；
- 确认已安装"WebSocket 协议"（部署说明里已有），否则实时通道会降级成长轮询，服务器的压力会成倍增加。

**SQL Server**（和 IIS 在同一台机器上时）：
- 最大服务器内存：给 Windows 和 IIS 留 4–6 GB。例如机器有 16 GB 内存，SQL Server 设 10 GB；32 GB 设 24 GB；
- 并行度：`cost threshold for parallelism` 设为 50，`MAXDOP` 设为 2（4 核机器）或 4（8 核以上）。这个系统是大量短查询，默认值（5 / 0）会让一些小查询也走并行，白白多占 CPU；
- 打开 Query Store（`ALTER DATABASE shizhong SET QUERY_STORE = ON`），以后查慢查询方便；
- 索引：`0902_perf.sql` 会在程序启动时自动执行。每周更新一次统计信息、整理一次索引碎片（可以用 SQL Server 代理作业，或者 Ola Hallengren 的维护脚本），并做好备份（完整备份 + 日志备份）；
- 可选：`ALTER DATABASE shizhong SET READ_COMMITTED_SNAPSHOT ON`（需要在维护时间做，执行时会断开所有连接）。本次开启它之后重跑了全部 14 个资金正确性测试，全部通过，吞吐基本不变。它的好处是读数据不再被写数据阻塞，可以进一步降低阻塞和死锁的可能；代价是 tempdb 占用多一些。修复之后不开也没有问题，所以列为可选。

**Cloudflare**：
- WebSockets 保持开启；
- `/api/*`、`/hubs/*`、`/core/server.js`、`/data/*` 不要缓存（它们是按用户生成的，程序已经返回 `no-cache` / `no-store`）。图片、`/assets`、`/vendor`、`*.css`、`*.js`（带 `?v=` 版本号的）可以缓存；
- 速率限制规则：例如 `/api/auth/*` 每个 IP 每分钟 20 次；另外可以对 `/api/*` 设一个宽松的总体限制，防止被刷接口。

**预计容量**（按这次的数字大致推算）：在单独一台 4–8 核、16–32 GB 内存的服务器上（IIS 和 SQL Server 放在一起），支撑**几千名注册会员、几百人同时在线、上千个实时连接**没有问题。需要注意的是 App 集中启动的高峰（本机约 45 次/秒），以及单个直播间集中刷礼物（约 100 次/秒）。会员增长到数万人之前，需要先处理第 9 节第 2 条和第 5 条（启动数据和 people / posts 数据的体积），然后在正式服务器上重新压测。
